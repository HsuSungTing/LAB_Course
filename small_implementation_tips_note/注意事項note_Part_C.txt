4. Latency 是我們目前很不擅長的部分之一，其中最重要的一點是 SRAM 的連續讀取。

a. SRAM 的連續讀取對 Latency 幫助最大，差異非常大。舉例來說，若要存一張 15x15 的 Image，每次讀出 10x10，如果一次只讀一筆 Data，Latency 會比較長。

b. 因此，在一個 Word 裡面盡可能存多筆 Data，將它們拼接起來是最有效的方法。

c. Lab4 的例子：許帝勳他們一次會讀四筆 Data，因為他們使用 32bit，而我們在 .18 製程的 Memory Compiler 中，一個 Word 最多 128bit，所以一次可以讀四筆 Data。

d. 這樣做可以直接將整個 Latency 除以四，相較於一次只讀一筆差異非常明顯。

e. 即便邊讀邊算(因為sram一筆一筆讀取還是太慢)，Pipeline 能省下部分 Latency但不是每個情況都非常好寫，如果一次可以讀多筆 Data，Latency 的改善效果會蠻大。

f. Lab5 和 Lab11 都有成功實作過這種方式：原本一次只推一筆 Data，改成一次推四筆 Data，只要一次 Shift 四格就可以，非常容易實作，不會過於困難。

g. SRAM Latency 的優化重點就是這種健康且熟悉的方式，不需要強迫自己過度複雜化。

h. 許多大佬為了省面積，並不會一次讀整張圖片來運算，這是非常好的做法，但對 Latency 幫助有限。另一方面，如果控制不好，像是 Mux 過多，也可能導致面積並未真正省下，因此以熟悉健康的方式寫最穩妥。

總結：對 SRAM Latency 最重要的是連續讀取多筆 Data，其餘不要有任何壓力。
