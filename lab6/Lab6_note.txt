表格的本質只是將所有可能的 case 系統性地列出，並沒有改變問題的複雜度，但能讓整個邏輯結構更一目了然。只要想使用表格，就可以用表格來整理思路，這樣能更容易掌握所有配對的可能性。

在設計複雜的 combinational logic 時，往往會遇到許多 dependency 的情況，例如 Huffman coding 或字串配對等問題，這些概念其實都與我們在 dynamic programming 中學到的原理相通。重點在於，我們要能夠感受出問題是否適合用表格整理，並在能力範圍內建立不過於龐雜的表格，讓它成為設計過程的良好輔助。

這次與張天神討論後，我們決定以表格的方式統計每個數字在各花色中是否出現。這樣的表格能幫助我們判斷「連續」的情況，對整題的演算法設計非常關鍵。整個問題本質上就是演算法題，透過依序判斷所有可能的組合，從上到下掃描表格，並根據表格的 row 順序（越上面的 priority 越高）依序進行選擇。

在設計的過程中，特別需要注意的是 combination 的部分。combinational logic 的設計其實與軟體邏輯非常接近，只是我們必須以硬體訊號（如 wire 或 reg）去記錄當前的選擇與狀態。不同之處在於，硬體的邏輯是分層展開的，每一層的輸出會接到下一層的輸入，如同一步步展開的流程。換句話說，任何軟體能完成的行為，combinational logic 都能實現，只是需要明確地展開成多層邏輯。

例如在挑選不連續字串中最大、第二大、第三大的數字時，第一層先找到最大值並記錄下來，然後將「用過」的資訊傳給下一層。下一層根據上一層的資訊繼續挑選，整個過程就像是把 for 迴圈展開成數個硬體步驟。這樣的設計方式其實比軟體更直觀，因為每個步驟都被具體地分層實現。

這也就是 combinational logic 除了做比較或運算之外，另一項非常重要的功能——「把複雜的行為連接成不同的層」。這與我們在 Level 1 所設計的結構相同：每一層的選擇會依賴前一層的配置結果，並一步步完成整個流程。邏輯上是完全一致的，只是展開方式不同。

最後，我們也注意到註教提供的 pattern 當中，平手的情況只會出現「兩人、三人、四人」或「九人」平手。這部分只要再與 GBT 確認即可。技術上，我們目前的作法是統計各種平手比例（如 1/2、1/3、1/4、1/9），並以 counter 的方式逐步累加。如果沒有平手，就直接以 1 累加。若要進一步簡化計算，也可以使用最小公倍數的方法，例如 36 作為最小公倍數，就能涵蓋所有可能的情況。這樣雖然笨一點，但在固定分母範圍內其實是可行且簡潔的實作方式。
